بطاقات أقسام مباشرة بدون قائمة جانبية، خط الجهاز، مدينون وفاتورة أكثر اختصارًا، بيع الجملة يبدأ بالآجل، وزر مصروف واضح مع تبسيط تسليم واستلام القاصة.


- تطبيق الهوية البصرية لمرجع `Abdulrahman_Solar_Premium_UI.pdf` على أقسام البرنامج: بترولي وأخضر وذهبي، بطاقات بيضاء، حقول وأزرار أوضح، وأيقونات SVG موحّدة. خط Noto Sans Arabic محلي بوزنين؛ رخصته في `public/fonts/OFL.txt`.

- الرئيسية تعرض مؤشرات حقيقية، متابعة التنصيب، إجراءات سريعة ومخطط المبيعات والكلفة. المخطط يستخدم الكلفة المثبتة للمبيعات وتوقيت بغداد، ولا يضيف أرقامًا تجريبية إلى البرنامج.
- الفاتورة على الكمبيوتر تقسم إلى نموذج وملخص بترولي ثابت على اليسار؛ على الموبايل تتحول المواد إلى بطاقات، وتتوفر تفاصيل المجموع عند الطلب. أزرار الحفظ ذهبية والمعاينة والحفظ والمشاركة ضمن نفس ملخص الفاتورة.
- تحديث الصندوق والأرباح والكشوف والأدلة والتقارير وبقية النماذج بنفس الهوية، وإعادة تصميم معاينة PDF مع تكبير وطباعة وحفظ ومشاركة. بيانات الوصل وحسابات العملات تبقى كما هي.
- إصدار واجهات فقط: لا توجد ترحيلات قاعدة بيانات أو إعادة تحويل أرصدة أو تغيير كلف تاريخية. آلية الحفظ المحمية، إعادة المحاولة، سعر الصرف المثبت، الكسور وعملة حساب المورد تبقى من V3.35.0.

التحقق: `node --test tests/*.test.mjs` و`npm run build`. الفحص `tests/premium-browser.mjs` يستخدم Chromium وPostgreSQL محليًا معزولًا، ويمنع الطلبات غير المعزولة من الوصول إلى الإنتاج. يفحص كتابة `125.50` وحفظ شراء الدولار وتعديله، إعادة تأكيد حفظ الصندوق دون تكرار، قاصتي IQD/USD، الصرافة، تسديد المورد وعكسه، الرصيد الافتتاحي والتكرار، تسديد الجملة والمنظومات، البحث والكشوف وتصفيات المدينين، PDF والتنزيل والمشاركة من الملف نفسه، والتنقل بعروض 360–1440 بكسل. بيانات الرسوم ونتائج قوائم المهام والمستخدمين في هذا الفحص fixtures محلية وليست بيانات إنتاج؛ لا ينشئ مستخدمين أو مهامًا في السحابة. الخيار `--visual` يعيد فحص واجهات الأقسام على قاعدة fixture موجودة، دون إعادة تسجيل الحركات. تحميل خط نافذة المعاينة يُراجع بصورة مستقلة دون اعتراض الشبكة بسبب تعارض Chromium مع اعتراض طلبات الخط في نافذة `about:blank`.

- أسعار شراء الدولار تقبل النقطة أثناء الكتابة وتحفظ السنتات. المبلغ الصحيح يظهر `125 $` والمبلغ الكسري يظهر `125.50 $`. الإجماليات والوصولات والمشتريات السابقة تظهر عملة الفاتورة الأصلية، وتظهر كلفة المخزون بالدينار بعنوان مستقل.
- عند اختيار مورد لفاتورة جديدة فارغة تتبع عملة الفاتورة والدفع عملة اتفاقه افتراضيًا، مع إمكانية اختيار عملة أخرى. دليل الموردين يعرض عملة الاتفاق والرصيد والقيمة الدفترية، ويتطلب تحديد العملة عند إضافة المورد ويمنع الاسم المكرر. تغيير عملة حساب قائم يبقى عبر مراجعة تحويل الرصيد المحمية.
- تسديد الجملة يستخدم نفس نمط تسديد المنظومات: اختيار العميل بالمعرّف، كامل الحساب والرصيد الافتتاحي، قبض أو إضافة غير نقدية، رمز للرصيد الحالي، وحفظ وPDF ومشاركة دون تكرار.
- قائمة جانبية للكمبيوتر وتنقل سفلي وقائمة أقسام للموبايل، بأيقونات SVG، ألوان واضحة، أزرار وحقول متسقة وجداول تتحول إلى بطاقات عند الحاجة. تبقى الأقسام المعروضة حسب الصلاحيات.
- الترحيل `supabase/migrations/20261017213648_unified_cash_and_supplier_directory.sql` يضيف طلبات مالية خاصة RLS وإجراءات محمية، ويربطها بالنسخ الاحتياطية والتصفير. لا يغير مبالغ الفواتير أو كلف المخزون أو الأرصدة التاريخية.

التحقق: `node --test tests/*.test.mjs` و`npm run build`، و`tests/finance-rollback.sql` داخل قاعدة PostgreSQL محلية معزولة، مع فحوص العملات والمنظومات السابقة. `tests/finance-browser.mjs` يختبر المتصفح → PostgreSQL للكتابة بالبوينت وحفظ الشراء والصندوق والصرافة والتسديدات والكشوف وتصدير PDF والمشاركة وفقد رد الحفظ والتنقل بعروض 360–1440 بكسل. قوائم التجهيز والمهام تستخدم نتائج فارغة في فحص الواجهات؛ هذا الفحص لا ينفذ تنصيبًا ميدانيًا فعليًا.

- الترحيل `supabase/migrations/20261017210306_system_payment_account_and_invoice_links.sql` يضيف تخصيصًا اختياريًا وجدول طلبات RLS خاصًا، ويمنع تعديل/حذف التسديد مباشرة وحذف فاتورة مرتبطة به، ويدمج تدقيق الطلبات في النسخة الاحتياطية والتصفير المحمي.

# V3.34.0 · حساب المورد بعملة الاتفاق + قاصتا الدولار والدينار

- عملة حساب المورد IQD أو USD، مستقلة عن عملة فاتورة الشراء أو التسديد. من «إضافة ← إضافة الموردين» يختار المدير العملة، ويراجع تحويل الرصيد بسعر محدد قبل الاعتماد. الحسابات الحالية تبقى IQD حتى يحدد المدير الاتفاق الفعلي؛ لا يُفترض أن شراءً سابقًا بالدولار يعني أن الحساب دولاري.
- الصرف اليومي يُنسخ داخل الحركة، وتغييره يحتاج صلاحية exchangeRateEdit أو المدير. الفواتير والتسديدات تحفظ المبلغ الأصلي، الصرف، مبلغ عملة الحساب، وصاحب القاصة. المصاريف الإضافية للشراء بالدينار وتشملها كلفة الفاتورة وحساب المورد.
- قاصة USD فعلية لكل مستخدم: شراء/بيع الدولار مقابل قاصته IQD، وإضافة/سحب رأس مال USD للمدير. لا يُخصم تسديد الدولار من قاصة الدينار. رصيد الدولار يُقيّم بمتوسط كلفته الدفترية، ولا تُحسب إضافات رأس المال ربحًا.
- حسابات الموردين تحفظ الرصيد الاسمي والقيمة الدفترية بالدينار. عند التسديد تُقفل القيمة الدفترية للجزء المسدد، ويظهر فرق الصرف المحقق منفصلًا في الأرباح؛ تبقى كلفة المخزون ومتوسطها وأرباح المبيعات السابقة ثابتة. لا توجد إعادة تقييم تلقائية بسعر اليوم.
- تغيير اتفاق عملة مورد ذي رصيد يقفل سجل العملة السابقة ويفتح الرصيد المحول بسجل جديد، مع حفظ القيمة الدفترية وتوزيع المستخدمين وتدقيق الطلب. يمكن مراجعة السجلات السابقة في كشف المورد. تعديل/حذف وصل له حركات مورد لاحقة أو حركات دولار لاحقة محظور؛ تُسجل حركة تصحيح مستقلة.
- تقرير أرصدة الموردين يفصل مجموع IQD عن USD، ويصدّر العملة مع كل رصيد وآخر دفعة. كشف المورد ووصولاته تدعم المعاينة والحفظ والمشاركة من ملف PDF نفسه. الحركات القديمة غير المرتبطة تبقى في ملحق مستقل.
- واجهة الموبايل بثلاثة أعمدة وأيقونات SVG مميزة، بطاقة عنوان أصغر، وقوائم وأرصدة ونماذج أكثر تقاربًا مع أهداف لمس وحقول واضحة.
- ترحيل قاعدة البيانات: `supabase/migrations/20261017144659_supplier_multicurrency_wallets.sql`. يضيف سجلات RLS خاصة ولا يمنح العميل كتابة مباشرة؛ يدمجها مع النسخة الاحتياطية/التصفير المحمي. تعاد الطلبات بنفس UUID دون تكرار الخصم.

التحقق: `node --test tests/*.test.mjs`، واختبارات PostgreSQL `tests/fx-rollback.sql`، والمتصفح→قاعدة محلية `tests/fx-browser.mjs`، والبناء الإنتاجي. سكربت `tests/run-fx.mjs` يحتاج نسخة قاعدة محلية من fixture الموردين السابقة؛ يُستخدم اسم `solar_*` معزول.

## V3.33.0 — المدينون وكشف العميل والتصدير وإضافات المورد

- تقرير المدينين حسب المستخدم المسؤول عن الزبون، مع اختيار الكل أو الجملة أو المنظومات، وإجماليات مستقلة وتجميع حسب المستخدم. التسديد المقبوض من مستخدم آخر يبقى ضمن كامل حساب الزبون.
- الحركة ذات معرّف زبون محذوف لا تُنسب تلقائيًا إلى حساب جديد يحمل الاسم نفسه. تعرض الحركات غير المرتبطة في سجل مستقل وملحق PDF، مع المسؤول والتاريخ والأثر، ولا تُضاف إلى مجموع أرصدة الحسابات المسجلة. لم تعد تمنع معاينة التقرير وحفظه ومشاركته.
- الأسماء القديمة بدون معرّف تُربط للقراءة فقط عندما تطابق اسمًا موحدًا فريدًا؛ يشمل ذلك المسافات والألف والتشكيل. الحساب الصريح الصحيح له الأولوية. لا يعيد الترحيل كتابة الأسماء أو المبالغ أو التسديدات.
- كشف العميل يستخدم قائمة بحث فورية بالاسم والهاتف والأرقام العربية وصيغ الهاتف العراقي، والاختيار بالمعرّف. كتابة بحث جديد تلغي العميل السابق لمنع عرض كشفه مع اسم البحث الجديد. الدليل محمي بصلاحية كشف العميل ومستقل عن صلاحية إضافة الزبائن، ولا يتوقف عند 1000 حساب.
- كشف واضح لافتتاح المدة والحركات المدينة والدائنة والرصيد النهائي، مع اختيار الفترة وتبويبات المبيعات والتسديدات. الرصيد الجاري يشمل كامل الحركات؛ يذكر المستند ذلك عند اختيار تبويب جزئي.
- تصميم جديد للتقريرين: ألوان زرقاء وخضراء عالية الوضوح، أزرار مع أيقونات، فلاتر مرتبة، جداول للكمبيوتر وبطاقات للهاتف. شريط الرجوع ضمن تدفق الصفحة لمنع تداخله مع الحقول.
- المعاينة والحفظ والمشاركة تستخدم نفس ملف PDF المحضّر للاختيارات الحالية. تجهيز الملف مسبقًا يحافظ على صلاحية نقرة المستخدم للمشاركة المباشرة في المتصفحات الداعمة؛ يتاح تنزيل الملف للمشاركة من الملفات عند عدم دعم المشاركة المباشرة.
- إعادة تسمية الزبون تحتفظ بالحركات القديمة المطابقة، وتبقى حماية الافتتاحي والصلاحيات والطلبات المكررة من V3.32.0.

- تسديد المورد يتضمن اتجاهين: تسديد نقدي ينقص المستحق ويخصم من القاصة، وإضافة غير نقدية تزيد حساب المورد دون خصم نقدي، حتى مع رصيد قاصة صفر. أسباب الإضافة: مصروف إضافي أو حساب قديم أو أخرى، مع تفاصيل إلزامية.
- الإضافة تحفظ كحركة مستقلة مع وصل ورصيد قبلها وبعدها، وتظهر بعنوانها الصحيح في كشف المورد وتقارير الأرصدة. لا تغير كميات المخزون أو كلفه. يمكن تعديلها مع حفظ القيمة السابقة في سجل الطلبات؛ لا يتحول وصل نقدي إلى إضافة أو العكس عند التعديل.
- قراءة حساب المورد وأثر القاصة من الخادم، وفحص المبلغ والصلاحيات والملكية والرصيد النقدي عند التسديد. إعادة المحاولة بعد فقدان الرد تستخدم نفس الطلب وتعيد نفس الوصل، وأزرار PDF في النموذج لا ترسل عملية حفظ.

## Push notifications (V3.3)

- Assignment of a system invoice to an engineer creates a notification for that engineer.
- A transition from in_progress to completed creates a notification for transactions.created_by (the invoice creator), independently of the cashbox owner.
- Each person must click “تفعيل إشعارات الموبايل” and grant browser permission on their device. The UI includes an explicit self-test, device opt-out and a private inbox.
- Opening a notification navigates to the installation file. Staff with system permission can view their own files; financial approval still requires installations permission.
- Push payloads contain generic task messages, no customer names, prices or cashbox balances. Service-worker account binding blocks messages for another account; logout clears the binding, closes visible notifications and unsubscribes.
- Database triggers create a durable per-device outbox. pg_net wakes the Edge Function after commit, and pg_cron retries due deliveries every minute with a lease, bounded exponential backoff and a maximum of five attempts. Expired subscriptions are removed.
- VAPID keys and the random worker token are stored in Supabase Vault under solar_push_vapid_public, solar_push_vapid_private and solar_push_worker_token. They are not committed to this repository.
- Deploy supabase/functions/solar-push with JWT verification disabled: its body requires the private worker token using constant-time comparison. Worker configuration/claim/finish RPCs are executable only by service_role. No user token can invoke the dispatcher.
- The private delivery table deliberately has no client RLS policies. Only trusted worker RPCs access it.
- Run tests/push-rollback.sql to validate routing, private inbox access, queue leasing and retries without sending a notification or retaining test records.
- Verification: hosted worker authentication and encryption self-test succeeded. Local browser tests covered activation, test request, real service-worker display using synthetic payloads, task navigation and opt-out. Receipt on a physical phone requires that device's permission and subscription.
- Mobile OS notification settings, connectivity, and browser background restrictions still control final display; provider acceptance is not proof a person read the message.

## This update (V3.2)

- Engineers receive only their assigned job details and unpriced material lists through a guarded RPC. They do not load products, transactions, cashboxes, costs or sale prices.
- Restrictive RLS policies deny engineers financial tables and constrain staff transactions, invoice items and cash ledger entries to their cashbox ownership. Administrators retain the aggregate view.
- Cashbox totals and movement lists use the same owner rule (cashbox_user_id, falling back to created_by); administrator deposits into a staff cashbox appear in that staff ledger.
- Installation stages: scheduled, in progress, report awaiting review, closed. Engineer reports include completion checks, notes and itemized task expenses.
- The server validates the assigned engineer, manager permission, state transition and expected revision. Row locks prevent double submissions. Final approved expenses replace the previous amount when reopening a job.
- Authorized staff manage installation files belonging to their cashbox; an administrator can manage all files.
- Closing a file recognizes approved installation cost; an actual cash payment is recorded separately through cashbox movements, preserving the existing accounting behavior.
- System invoice creation now awaits the transactional save and validates the engineer, appointment, address and inventory quantities.
